## 2026-11-02 — Siamese U-Net adopted over early-fusion baseline
Decision: the Siamese U-Net (shared ResNet34 encoder, |pre−post| skip features) is the primary change-detection model.
Evidence (KATE-CD test, 38 images, thresholds chosen on validation by F1 → 0.2 for both models; `reports/comparison_siamese_vs_baseline_f1.json`): F1 0.602 vs 0.502, paired-bootstrap ΔF1 = +0.104 [+0.038, +0.166], IoU +0.099 [+0.037, +0.155], recall +0.099 [+0.015, +0.175]; precision +0.096 [−0.003, +0.196] (not significant). The same direction holds with F2-selected thresholds (ΔF1 +0.081 [+0.032, +0.135]).
Caveat: single training run per model (no seed variation); 38 test images, so absolute numbers carry wide CIs.

## 2026-11-02 — Uncertainty method: 8-view TTA
Decision: pixel uncertainty = std over 8 dihedral test-time-augmentation views (rot90 × flip); the mean over views is the reported probability. Implemented in `quaketriage/uncertainty.py`, used by `infer_area.py`.
Evidence (`reports/uncertainty_{baseline,siamese}_{validation,test}.json`, 4 model×split combinations): TTA has the lowest Brier score in all four and by far the best error awareness (mean uncertainty on wrong ÷ correct pixels: 13.9–20.9 vs 5.2–7.2 for MC Dropout) while keeping F1 on the Siamese model (val 0.562 vs 0.555 single pass). MC Dropout has a marginally lower ECE (Siamese val 0.0103 vs 0.0110, test 0.0062 vs 0.0079; ECE is dominated by the ~96 % easy negatives). For the baseline, TTA cost 2–2.5 F1 points at a fixed threshold.
Caveats: MC Dropout was applied at inference only (checkpoints were trained without dropout), so it was not tested at its best; a dropout-trained Siamese run on Kaggle could re-open this. TTA needs 8 forward passes per tile (vs T=10 for MC Dropout), so cost is comparable.

## 2026-11-02 — Threshold selection rule
Decision: the operating threshold is chosen on the validation split, never on test. Default: F1-optimal (0.2 for both models). The checkpoint's stored 0.5 was never tuned (the Kaggle sweep result went only to the history JSON), so the earlier 0.5 numbers are kept only as reference (`reports/metrics_*.json` without suffix).
F2 (recall-weighted) was evaluated as requested (`reports/metrics_*_f2.json`): the optimum keeps hitting the edge of the search grid (0.05 with the first grid; 0.01 baseline / 0.02 Siamese after extending it to 0.01), so the selection is unstable with only 44 validation images, and probabilities that low are not a trustworthy operating point. F2 is therefore offered as a *high-recall profile* (Siamese test: recall 0.588, precision 0.598), not as the default.

## 2026-11-02 — RAG source text: no OCR needed
Decision: extract INSARAG Vol II/III and AFAD TAMP with `pypdf` directly (`scripts/extract_rag_text.py`); `pypdf` moved from the `agent` extra to base dependencies.
Reason: all three PDFs have a text layer (≤2 low-text pages each, outlines present), so `pytesseract` (not installed) is unnecessary.

## 2026-11-02 — Guard SSIM threshold recalibrated 0.4 → 0.05
Decision: `thresholds.guard_ssim_min` = 0.05.
Reason: block-SSIM between pre/post on unchanged areas of KATE-CD pairs (different sensors, sun angles, off-nadir) has median 0.24 (val) / 0.32 (test) and 5th percentile 0.06–0.08; the initial guess of 0.4 would reject 76–84% of the pairs the model was trained and evaluated on. The Kilis demo crop scores 0.20–0.27, i.e. typical for this data. Raw SSIM therefore only catches gross misregistration (≈0), not parallax; a feature-based co-registration check is a possible future improvement.

## 2026-11-02 — RAG retrieval: multilingual-e5-small + BM25 hybrid, 700-char chunks
Decision: embed with `intfloat/multilingual-e5-small` (local, free, 384-d; `query: `/`passage: ` prefixes) and fuse dense cosine with BM25 by reciprocal-rank fusion; chunks of ~700 characters (17 % overlap) that never cross a numbered heading.
Evidence (`reports/rag_ablation.json`, `reports/metrics_rag.json`, 10 gold questions in `configs/rag_golden.json`): the planned `paraphrase-multilingual-MiniLM-L12-v2` dense-only baseline scored recall@5 0.6–0.7 / MRR 0.45–0.50; e5-small hybrid 700 scores recall@1 = recall@5 = 0.8, MRR 0.80. MiniLM hybrid 700 ties it (0.8 / 0.80) and e5-small dense 400 reaches recall@5 0.9 only through one cross-lingual hit, so with 10 questions these are statistically indistinguishable; e5 was preferred because it is trained for retrieval at the same size.
Known failures (kept visible): (1) the Vol III field guide is a table (Action | Description | Reference), so a question about "what to do before a technical search" retrieves Vol II text instead; (2) an English question about a Turkish-only passage (TAMP) is not matched by these small models — the agent should phrase queries in the document's language (LLM-side translation, Week 6).
Corrections made on the way: the PDFs have no outline (the earlier `has_outline: true` flag was wrong; sections come from heading detection in `rag/chunk.py`); numbered list items ("2. USAR Teams may…") are no longer mistaken for headings; gold question 4 was widened after reading INSARAG Vol II 6.1/6.2, which answers it better than the Vol III one-liner. The gold set is small (10), so it guides but cannot prove model superiority.

## 2026-11-02 — Building-level evaluation = noise-sensitivity of the planning pipeline (not model accuracy)
Decision (the project owner, combined option): (1) HOTOSM destroyed-building polygons are the ground truth and, with deliberately added noise, also the *simulated detector* for Antakya (`buildings/simulate.py`: miss rate, false-alarm rate, optional size-dependent misses; probabilities consistent with the decision, uncertainty peaking near the threshold — all shapes are assumptions). (2) `reports/metrics_building.json` is flagged `SIMULATED_DETECTOR` and reports how building-level precision/recall, person-weighted recall and verification-queue size change over a miss × false-alarm grid (5 seeds). (3) Damage-model accuracy is claimed on KATE-CD only (`reports/metrics_baseline*.json`, `metrics_siamese*.json`); the Kilis crop is a real-imagery pipeline demo.
Reason: using HOTOSM as both detector input and validation would be circular and would show perfect numbers; with injected noise the same data answers a real question for Weeks 5–7 (how robust are priorities and routes to detector errors).
Caveat: HOTOSM lists only *destroyed* buildings and is incomplete, so "not destroyed" ground truth contains unmapped damage; false-alarm rates are therefore upper-bound-ish.

## 2026-11-02 — Antakya OSM download used the wrong bbox (fixed)
Finding: `scripts/download_demo_area.py` passed `bbox` to osmnx as (N, S, E, W), the osmnx 1.x order; the installed osmnx 2.1.1 expects (left, bottom, right, top). The Week-1 buildings (1876) and road graph (717 edges) therefore covered lon 36.25–36.30 / lat 36.10–36.15, ~10 km away from the HOTOSM destroyed buildings (732 in lon 36.13–36.18 / lat 36.16–36.26), with zero overlap. Caught at the start of Week 4 when checking building/HOTOSM overlap.
Fix: script now passes `DEMO_BBOX` unchanged. The old files were moved (not deleted) to `data/raw/demo/_wrong_bbox/`; the correct data is re-downloaded when Overpass is reachable (all public Overpass endpoints timed out on 2026-11-02).
Lesson: after every download, assert that the result lies inside the intended bbox (added to `check_data.py` once the data is back).

## 2026-11-10 — Demo depot = OSM "AFAD" building (scenario assumption)
Decision: `routing.depots` in `configs/default.yaml` holds one demo depot, [lon, lat] = [36.17179, 36.20657], the centroid of the OSM building tagged `name=AFAD`, `office=government` (way 1139261935, Antakya), read from Overpass on 2026-11-10. Code converts it to the project CRS and snaps it to the nearest node of the road graph (`planning/roads.py`; 58 m snap distance, node in the largest strongly connected component).
Reason: coordinates are taken from a real mapped object instead of being invented, and an AFAD site is a plausible staging area. It is **not** a real operations centre or a statement about where teams actually staged — only a scenario assumption for the planning demo. Other candidates found in the area were AFAD seismic-station nodes (not operational sites) and no OSM fire station.
Sensitivity (`reports/depot_sensitivity.json`, 5.895 buildings): moving the depot to the hospital (way 366665647) or town hall (way 311391399) changes the whole TOPSIS ranking moderately (Spearman 0.72 / 0.84) but barely changes the top of it (top-100 overlap 0.99, top-500 0.98 / 0.97), because damage probability and people carry 70 % of the weight and the depot-distance criterion only reorders buildings of similar urgency. Depot choice therefore matters more for routing (Week 5, VRP) than for the priority list.

## 2026-11-10 — Debris risk on roads: penalty + closure rule (assumption)
Decision: a building is a debris source if `damage_prob > 0.5` and `floors >= 3`; every road segment within 50 m (`routing.debris_risk_buffer_meters`) of a source has its travel time multiplied by 3, and a segment near >= 5 sources is closed (`travel_time_adj = inf`). Implemented in `planning/debris.py`; the road graph keeps its largest strongly connected component (`planning/roads.py`) so the depot and buildings stay mutually reachable before closures.
Reason: the plan asks for "closed or penalised" segments near heavily damaged multi-storey buildings; a soft penalty keeps routes feasible in dense areas while a hard closure models streets that are likely impassable. All numbers are scenario assumptions in the config, not calibrated against real debris data. On the Antakya demo set (498 sources / 5,895 buildings) 7.3 % of the 30,600 edges are penalised and 1.1 % closed.
Caveat: closures can cut off parts of the graph; the VRP step must treat unreachable buildings explicitly (skip + report), not crash.

## 2026-11-10 — VRP: top-N candidates, cached matrix, closure rule makes buildings unreachable
Decision: the prize-collecting VRP (`planning/vrp.py`) only considers the top `routing.candidate_n` (400) buildings by TOPSIS priority; skipping a building costs its priority (scaled to int), travel seconds only break ties. One shortest-path travel-time matrix (scipy Dijkstra on the debris-adjusted graph) is computed for the largest candidate set and cached in `outputs/cache` (key = node list + edge weights); smaller N use sub-matrices. 4 teams, 6 h, 30 min per building, 30 s solver limit. Buildings that cannot be reached from / returned to the depot are dropped and counted.
Evidence (`reports/metrics_planning.json`, SIMULATED detector, scenario depot): N = 200 / 400 / 500 / 1000 all visit 44 buildings and collect priority 26.78 / 26.80 / 26.80 / 26.80 — the mission length (4 teams x 6 h / 30 min) caps visits at ~48, so N beyond 200 adds nothing; N=400 is kept as a safety margin. Persons reached differ by <1 % (3,914 vs 3,891) and are not monotone in N, because the objective is priority, not persons, and the time-limited search is not exactly reproducible.
Finding (needs a decision): the closure rule (>= 5 debris sources within 50 m) cuts 1,139 of 5,895 buildings (19 %) off from the depot — 96 of the top 400 — although with no closures all are reachable. Penalty-only (x3 travel time, no closures) collects priority 27.82 vs 26.80 with closures (+3.8 %). The unreachable count grows with N (37 / 96 / 126 / 213) because the most damaged areas are also the densest. Real teams would drive up to the blockage and continue on foot; the current model treats those buildings as lost. Options for later: walking leg after the nearest open node, or a higher `debris_block_count`. Not changed yet — it is a scope/assumption decision.

## 2026-11-10 — Walking leg for buildings cut off by closed roads (assumption) + baselines
Decision: a building whose street node cannot be reached by vehicle (closed edges) is reached by driving to the nearest drivable node and walking the rest along the street network (closed streets included) out and back at `routing.walking_speed_kmh` = 3 km/h (loaded, over rubble); the walking time is added to the 30-min intervention at that stop. Beyond `routing.max_walk_m` = 500 m the building stays unreachable. The closure threshold (`debris_block_count`) was not touched. Both walking values are assumptions, not measurements.
Evidence (`reports/metrics_planning.json`, SIMULATED detector, scenario depot, N = 400): priority collected / persons reached / unreachable among candidates — no closures 27.82 / 3,969 / 0; closures without walking 26.80 / 3,891 / 96; closures with walking 27.80 / 3,969 / 0 (96 stops need walking). Over all 5,895 buildings unreachable: 0 / 1,139 / 0 — everything cut off lies within 500 m of a drivable node, so the limit does not bind here. Walking recovers essentially all of the loss caused by closures.
N sweep (closures + walking): 200 / 400 / 500 / 1000 → priority 27.75 / 27.80 / 27.75 / 27.26 (44 / 44 / 44 / 43 visits). The slightly worse N=1000 is the time-limited local search not converging in 30 s on the larger problem, not a modelling effect; N = 400 stays.
Baselines (same candidates, travel/service times, 4 teams, 6 h; `planning/baselines.py`): VRP priority 27.80 / persons 3,969; nearest-first greedy 18.54 / 1,453 (44 visits); random (30 seeds) 15.43 ± 0.59 / 1,455 ± 166 (35.9 visits). The VRP collects 1.5x the priority of greedy and 1.8x that of random with the same number of visits, mostly by choosing high-priority buildings rather than by visiting more. Greedy and random ignore priority by design; a "highest priority first" rule was not added (out of scope).
Caveat: all numbers come from simulated damage probabilities and a scenario depot; they describe planning behaviour, not rescue outcomes.

## 2026-11-10 — Priority-first baseline; vehicle legs never cross closed edges
Baseline: "highest priority first" (same candidates, times, teams; ignores distance; `planning/baselines.py`) collects priority 23.29 / 3,273 persons in 36 visits, versus VRP 27.80 / 3,969 (44 visits), nearest-first 18.54 / 1,453 and random 15.43 ± 0.59 / 1,455 ± 166 (`reports/metrics_planning.json`, SIMULATED detector). The VRP beats the best simple rule by 19 % priority; priority-first loses mostly because long transfers cost it 8 visits. Baselines were recomputed with `plan_routes.py --baselines-only`, keeping the stored (non-reproducible) VRP numbers; greedy and random values are unchanged by construction (deterministic).
Check: `drive_edges` hides closed edges from the path search; a unit test verifies on the real plan that no driving leg of any team uses an edge flagged `blocked` (no violation found), and that closures exist so the test is not vacuous. Only walking legs go through closed streets.

## 2026-11-10 — LLM adapter: provider fallback on 429, disk cache, no live call in tests
Decision: `agent/llm.py` wraps Gemini and Groq behind one `complete(prompt, system)`; provider/model come from `.env` (`LLM_PROVIDER`, `LLM_MODEL`, optional `LLM_FALLBACK_PROVIDER`, `LLM_FALLBACK_MODEL`), keys from the environment only. 429/5xx/connection errors are retried with exponential backoff (`llm.max_retries`, `llm.retry_base_delay`); if a backend stays rate-limited the next one is tried; other 4xx fail immediately without echoing request content. Identical requests are cached under `outputs/cache/llm` (key = provider, model, system, prompt, temperature) and do not count as LLM calls; `LLM.calls` / `cache_hits` feed the Week-7 "LLM call count" metric. Default temperature 0.
Reason: the plan asks for retry, cache and Groq fallback; caching also keeps evaluation runs cheap and repeatable on free tiers. Tests use fake backends, so no key or network is needed and nothing is spent.

## 2026-11-10 — Agent tools: shared ToolContext, summaries instead of tables, deterministic sitrep
Decision: the nine tools (`agent/tools.py`) are plain functions `fn(pydantic_input, ctx) -> pydantic_output`. The building table, road graph, RAG index, constraints and last plan live in a `ToolContext`; the LLM only ever sees short summaries (counts, top-k rows, per-team stops). `ToolContext.call(name, args)` validates against the schema, records a trace entry (arguments, seconds, summary or error) and turns bad input into a `ToolError` the agent can read. `tool_schemas()` exports JSON schemas for function calling.
`write_sitrep` is a deterministic template over the pipeline state, so no number in the report is generated by the LLM; protocol citations (document + pages) come from the last `lookup_protocol` call, the SIMULATED-detector banner is added whenever the damage source was the simulator, and steps that were not run are listed in `missing_steps`.
`update_constraints` only records the change and returns the stale steps from an explicit map (`STALE_BY_CONSTRAINT`, e.g. `num_teams` -> `plan_routes`, `write_sitrep`; `weights` -> `prioritize_sites` onward; `damage_threshold` -> `score_buildings`), so the graph can re-run just those. A test enforces that every constraint has a rule. What-if road closures are circles (lon, lat, radius_m) applied to the debris-adjusted graph (`close_edges_near`).
`detect_damage(source="siamese")` runs the trained model on a GeoTIFF pair (summary statistics only, no building table: there is no OSM building set for the Kilis crop); `source="simulated"` is the Antakya demo path. The Siamese path is covered only through an injected runner in the tests and has not been run on real imagery from the tool yet.
Occupancy scenarios: `night` (04:17 factors, the default) and `full_occupancy` (`residents_day`, no time-of-day factor). Real-data smoke test (all tools, Antakya): 51 s, plan identical to the Week-5 result (44 visits, priority 27.80).

## 2026-11-10 — Guard enforced inside the tools; tool outputs always carry SIMULATED_DETECTOR and uncertainty
Decision: `prioritize_sites`, `plan_routes` and `write_sitrep` return `status="verification_required"` (no ranking, no plan, no priority table) when the image-quality guard failed; buildings above the uncertainty threshold (or without valid imagery) are held back in `verification_queue` and never dispatched, even if `score_buildings` was not called first (`ensure_scored`). Every tool output has `SIMULATED_DETECTOR`, `status`, `warnings` and `uncertainty` (filled by `ToolContext.call`); `detect_damage` states which detector produced the numbers. `update_constraints` removes stale steps from `done`.
Consequence: the Week-5 standalone metrics (`metrics_planning.json`) still include queue buildings; tool-level plans exclude them (3 of 4 dispatchable test buildings, 112 of 5,895 in Antakya), so tool plans can differ slightly from those reports.
Siamese from `detect_damage` ran once on the Kilis crop (31 s, 25 tiles, mean prob 0.004, 0.05 % of pixels above threshold, mean TTA std 0.0014); this also exposed and fixed a wrong `predict_tile` call in the untested runner.
Status: `agent/graph.py` (router + conditional edges, code-level quality gate, what-if re-run of stale steps, per-turn LLM-call/cache/latency log in `outputs/logs/agent_runs.jsonl`) is tested with a fake LLM (12 tests: language, skip-done steps, what-if, guard stop, injection, Kilis gate, citation clean-up, keyword fallback, metrics). Only the router and the protocol answer use the LLM; guard rules are in code.

## 2026-11-10 — Sitrep protocol query, demo conversations, citation check scope

The transcript script refuses to write if an environment secret appears in the text.

## 2026-11-10 — Sitrep protocol section, localized warnings, rough citation-support check
Sitrep protocol section: passages are clipped at sentence boundaries (a leading half-sentence is dropped; a single over-long sentence gets an ellipsis), only passages with >= 2 of the config keywords (`agent.sitrep_protocol_keywords`: triage, assess, worksite, search site, priorit, damage, marking) are shown, renumbered 1..k (max 3), and the section is omitted when none qualifies. A Turkish report that cites English (INSARAG) passages says so; they are not translated. In the demo, 1 of 5 retrieved passages passed (INSARAG Vol II 5.8 Worksite Triage). The keyword rule is crude and can exclude useful passages; it only guards against irrelevant ones.
Localized warnings: `ToolContext.lang` (set by the router each turn) drives all guard / verification warnings; the known guard phrases from `data/quality.py` are translated. Tool *errors* (`ToolError`, e.g. missing files) and `detector_note` stay English.
Sitrep now states the people awaiting verification: "112 buildings, ~967 people awaiting verification"; the same number is in `score_buildings` and `prioritize_sites` outputs.
Conversation 4 audit (INSARAG Vol II Man B p. 7, section 2.3): "The operations phase ... starts with arrival of a USAR Team at the Reception/Departure Centre (RDC) in the affected country, registration with the UCC/OSOCC, reporting to the LEMA (or NDMA)". The answer's claims (register with the UCC/OSOCC; report to LEMA/NDMA; this begins the operations phase) are supported and the citation [2] stays. The answer omits that arrival happens at the RDC and says "arrival in the affected country", so it is supported but incomplete; left unchanged on purpose.
`check_support` (rough): a cited sentence counts as supported if the cited passage contains all its acronyms/numbers and >= 50 % of its other content words (5-letter prefix match). It catches invented terms and wrong passages (tested) but not meaning, negation or omission, and it has false negatives: "This process marks the beginning of the operations phase" scored unsupported (synonym of "starts") although the passage supports it. It is a smoke test for the Week-7 citation metric, not a fact check; supported-claim rates must be confirmed on a hand-checked sample. Its result is logged per turn (`citation_support`).
Latency: the OR-Tools solve takes ~30 s per plan; Week-8 UI will cache plans by constraints (PLAN.md note) and show progress.
Demo transcript re-run: LLM answers were replayed from the cache of the first real run (6 Gemini calls) so conversation 4 stays identical; the cache records the original provider.

## 2026-11-10 — Two gaps found while writing the agent scenarios
(1) Follow-up questions when every step is still fresh (e.g. "show the route plan again") produced "no step has run yet" because the answer was built only from this turn's tool results; compose now falls back to the stored output of every fresh step (`ToolContext.outputs`). (2) `uncertainty_tau` was a what-if knob, so "set the threshold to 100" would have switched the verification queue off; it can now only be tightened (<= `thresholds.uncertainty_high`), and the request is rejected like any invalid constraint. Both have tests; scenarios A03 and N06/N07 check them end to end.
Scenario set (`eval/agent_scenarios.yaml`, 38): normal 7, what-if 8, bad image/guard 5 + 1 good-image control, protocol 8 (the same questions and gold pages as `configs/rag_golden.json`), off-topic 5, adversarial 4. Each turn states expected intent, language, the exact ordered tool list, stop reason and constraint subset; each scenario names forbidden behaviours (decision despite bad quality, dispatching unverified buildings, disabling the guard, secret leak, tools for off-topic input, citation to an unretrieved passage).

## 2026-11-10 — Agent evaluation run (Week 7)
Cold run (LLM cache emptied first), 38 scenarios, one run: task success 30/38, tool selection 45/48 turns, 0 forbidden-behaviour violations (every rule is checked in every scenario, each violation counted separately), 3/8 protocol answers cite the gold page, 0 dangling citations.
